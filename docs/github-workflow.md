# Mosaic GitHub 工作流规范

> 适用范围：所有参与 Mosaic 项目开发的成员（包括 AI Agent 协作）

---

## 一、分支策略

### 主要分支

| 分支 | 说明 | 保护规则 |
|------|------|---------|
| `master` | 生产主干，始终保持可发布状态 | 禁止直接 push，须通过 PR 合入 |
| `dev` | 集成开发分支，各功能分支合并目标 | 禁止直接 push，须通过 PR 合入 |

### 功能分支命名规范

```
<类型>/<简短描述>
```

**类型前缀：**

| 前缀 | 用途 | 示例 |
|------|------|------|
| `feat/` | 新功能开发 | `feat/skill-research` |
| `fix/` | Bug 修复 | `fix/sse-connection-drop` |
| `refactor/` | 代码重构（不改功能） | `refactor/orchestrator-cleanup` |
| `docs/` | 文档修改 | `docs/api-contract-update` |
| `chore/` | 构建、配置、脚手架 | `chore/add-eslint-config` |
| `test/` | 补充测试 | `test/skill-unit-coverage` |
| `hotfix/` | 生产紧急修复 | `hotfix/auth-token-expiry` |
| `release/` | 发布准备 | `release/v0.2.0` |

**命名要求：**
- 全部小写，单词用 `-` 分隔
- 描述简洁，3~5 个英文单词
- 不要带 issue 编号前缀（关联通过 PR body 实现）

## 二、分支生命周期

```
master
  └── dev（长期存在）
        ├── feat/xxx   ──PR──> dev ──PR──> master（Release 时）
        ├── fix/xxx    ──PR──> dev
        └── hotfix/xxx ──PR──> master + dev（紧急修复直接上主干）
```

### 标准流程

```bash
# 1. 从 dev 切出新分支
git checkout dev
git pull origin dev
git checkout -b feat/your-feature

# 2. 开发、提交（见 Commit 规范）
git add .
git commit -m "feat: 添加 Research Skill 执行逻辑"

# 3. 推送并创建 PR
git push -u origin feat/your-feature
# 在 GitHub 上开 PR，目标分支 dev
```

### Hotfix 流程

```bash
# 从 master 切出
git checkout master && git pull
git checkout -b hotfix/fix-description

# 修复后 PR 到 master
# master 合并后，同步 cherry-pick 或 PR 到 dev
git checkout dev
git cherry-pick <commit-hash>
```

## 三、Commit Message 规范

遵循 [Conventional Commits](https://www.conventionalcommits.org/) 规范：

```
<type>(<scope>): <subject>

[可选正文]

[可选 footer]
```

### type 类型

| type | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 文档变更 |
| `style` | 代码格式（不影响逻辑） |
| `refactor` | 重构 |
| `test` | 测试相关 |
| `chore` | 构建/工具/依赖 |
| `perf` | 性能优化 |
| `ci` | CI/CD 配置 |
| `revert` | 回滚提交 |

### scope（可选，推荐使用）

对应项目模块：`backend`、`web`、`admin`、`skill`、`llm`、`orchestrator`、`api`、`db`、`docs`、`ci`

### 示例

```
feat(skill): 新增 Deck Skill 幻灯片生成逻辑

- 集成 OpenAI GPT-4o 生成 outline 与 slide content
- 支持最多 10 页自动排版
- 依赖 strategy skill 输出作为上游输入

Closes #12
```

```
fix(sse): 修复客户端断连后 goroutine 泄漏问题
```

```
chore(ci): 添加 Go 单元测试 GitHub Actions workflow
```

### 规则

- subject 使用动词开头，中英文均可，建议中文（与用户沟通一致）
- subject 不超过 72 字符
- body 每行不超过 100 字符
- **不允许** `fix bug`、`update`、`修改` 等无意义提交信息
- **不允许**单次提交超过 500 行改动（拆分提交）

## 四、Pull Request 规范

### PR 标题

与 Commit Message 格式一致：

```
feat(backend): 实现项目并发编排引擎 V0.1
```

### PR Body 模板

```markdown
## 变更说明

<!-- 简述本 PR 做了什么，为什么这样做 -->

## 变更类型

- [ ] feat: 新功能
- [ ] fix: Bug 修复
- [ ] refactor: 重构
- [ ] docs: 文档
- [ ] chore: 构建/配置

## 测试情况

- [ ] 本地 lint 通过
- [ ] 单元测试通过 (`go test ./...` 或 `pnpm test`)
- [ ] 手动验证通过（描述验证步骤）
- [ ] 已补充/更新相关测试

## 关联 Issue

Closes #xxx

## 截图 / 录屏（如涉及 UI 变更）

<!-- 粘贴截图 -->
```

### PR 规则

- 每个 PR 只做**一件事**，保持小而聚焦
- PR 合并前必须通过 CI 所有检查
- PR 描述必须填写"变更说明"，不允许为空
- PR 不应包含与本次需求无关的改动
- AI Agent 提交的 PR 在 body 末尾注明 `> Generated by AI Agent`

## 五、分支保护规则（GitHub Settings）

在 GitHub → Settings → Branches 中配置：

**`master` 分支：**
- ✅ Require a pull request before merging
- ✅ Require status checks to pass before merging（需通过 `ci-backend`、`ci-frontend`）
- ✅ Require branches to be up to date before merging
- ✅ Do not allow bypassing the above settings

**`dev` 分支：**
- ✅ Require a pull request before merging
- ✅ Require status checks to pass（至少 `ci-backend` 或 `ci-frontend`）

## 六、版本发布规范

遵循 [Semantic Versioning](https://semver.org/)：`MAJOR.MINOR.PATCH`

| 版本号 | 变更类型 |
|--------|---------|
| `MAJOR` | 不兼容的 API 变更 |
| `MINOR` | 向后兼容的新功能 |
| `PATCH` | 向后兼容的 Bug 修复 |

### 发布流程

```bash
# 1. 从 dev 创建 release 分支
git checkout dev && git pull
git checkout -b release/v0.2.0

# 2. 更新版本号、CHANGELOG
# 3. PR 到 master
# 4. 在 GitHub 打 Tag + Release
git tag -a v0.2.0 -m "Release v0.2.0"
git push origin v0.2.0
```

## 七、AI Agent 协作约定

当使用 AI（Cursor、Claude Code 等）协助开发时：

1. **每个需求独立分支**：AI 辅助开发前，先明确分支名，由 AI 基于该分支操作
2. **AI 不直接 push 到 `master`/`dev`**：始终通过 feature 分支 + PR 流程
3. **AI 生成的 Commit 必须经人工审查**再 push
4. **PR Body 末尾标注**：`> Generated with AI assistance (Cursor Agent)`
5. **敏感文件检查**：AI 提交前确认未包含 `.env`、密钥、token 等敏感内容

## 八、快速参考

```bash
# 开始新需求
git checkout dev && git pull && git checkout -b feat/your-feature

# 日常提交
git add -p                             # 逐块暂存，避免提交无关内容
git commit -m "feat(scope): 描述"

# 推送并开 PR
git push -u origin feat/your-feature  # 首次 push
git push                               # 后续 push

# PR 合并后清理本地分支
git checkout dev && git pull
git branch -d feat/your-feature
```
